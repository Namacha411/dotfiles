# 論文解説記事の書き方(article への具体的適用)

このファイルは `explain-clearly` の9つの設計思想(読者を主語にする・ストーリーとして語る・結論先出し・分割統治・図表とリズム・比較とリスト・独自の視点・対立軸・たとえ話と具体例)を、**学術論文をHTML記事として解説する**という具体的な成果物に適用したものです。SKILL.mdの設計思想を踏まえたうえで、以下の記事特化の適用・テンプレート・出力仕様に従ってください。

## このスキルについて

実際に読まれている人気の論文解説記事を読み込んで抽出した「良い記事に共通するパターン」に基づいている。ゴールは論文の内容を漏れなく要約することではなく、**読者が挫折せずに「なるほど、そういうことか」まで辿り着けること**。同じ論文の内容でも、書き方次第で読了率も理解度も大きく変わる。

## 記事を書き始める前に

- 論文の本文(PDF・URL・アブストラクトなど)がまだ渡されていない場合は、まずそれを確認する。本文を読まずに一般論だけで書き始めない。
- 論文を読んだら、次を自分の言葉で整理してから書き始めるとよい: ①解決したい課題は何か ②既存手法の何が不十分か ③提案手法のコアアイデアを一文で言うと何か ④主要な実験結果・貢献は何か ⑤限界・今後の課題は何か。ここが曖昧なまま書き始めると、記事も論文の逐語訳のようになってしまう。
- 想定読者(その分野にどれくらい詳しい人向けか)が指定されていなければ、「その技術領域にある程度触れたことがあるエンジニア」を基本の読者像とし、専門用語を使う際は一言説明を添える。

## 9つの設計思想を記事に適用する

設計思想そのものと「なぜそうするのか」は SKILL.md に書いてある。ここでは、論文解説記事という形式で特に効く適用の仕方だけを示す。

### 1. 常に「読者」を主語にして書く
「はじめに」は論文の紹介からではなく、読者が抱えていそうな疑問・課題から始める(「〜で困ったことはないだろうか」「〜と思う人も多いはずだ」)。論文の著者が何をしたかは、その疑問への答えとして登場させる。

### 2. 「差分」ではなく「ストーリー」として語る
論文は基本的に先行研究との「差分」を書くことが目的になっている。記事ではそれをそのまま説明せず、その分野がどんな歴史的経緯・課題の連鎖を辿って提案手法に至ったのかを一本のストーリーに再構成する(例: 「まずAという課題があった → Bが提案された → しかしBには◯◯という限界があった → そこで本論文のCが生まれた」)。事前知識やモチベーションのセクションは箇条書きの羅列で終わらせない。論文自体が差分の説明に終始していても、記事側では周辺の歴史的文脈を(必要なら追加で調べて)補ってよい。

### 3. 結論・全体像を先出しする
「はじめに」より前に「概要」を置き、この技術が具体的に何であり、何に応用できるのかを一言で示す。各セクションも、コアコンセプトを最初の1〜2文で提示してから詳細に踏み込む。

### 4. 分割統治的にセクションを分ける
論文の構成に沿いつつも、1セクションで扱う情報量を小さく保つ。「事前知識 → モチベーション → アイデア → 詳細 → 難しさ」のように、読者の理解が一段ずつ積み上がるように分解する。

### 5. 図表を積極的に使い、文章のリズムを整える
図が多い記事は明確に読みやすいと評価されている。可能な限り、論文中の概念を自分で図解する。文章が同じトーンで長く続く箇所(目安: 見出しなしで3〜4段落以上)は、図・表・箇条書き・区切り線・空行などを挟んで視覚的なリズムを作る。

### 6. 比較・リスト・箇条書きを多用する
「既存手法 vs 提案手法」「手法Aの利点/欠点」は比較表にする。実験結果も、論文の表を丸写しするのではなく、言いたい一点が見える行・列だけに絞って作り直す。

### 7. 著者独自の視点・工夫を入れる
最も評価が高い記事は、論文の要約で終わっていない。独自の切り口、感想、簡易実装(ミニコードで実際に動かしてみる)など、「この著者が読んで咀嚼した結果」が乗っている。可能なら、簡単なコードで再現・検証するセクションを入れると理解が一段深まる。

### 8. 対立軸(二項対立)を立てて論を構成する
記事の早い段階(「はじめに」やモチベーションのセクション)で対立軸を明示すると、以降のセクションがその軸で整理され読みやすくなる。候補としては、既存手法/提案手法、手法A/手法B、想定される反論とその回答、ライバル論文との位置づけ、楽観的な見方/懐疑的な見方などがある。仮想敵を立てるのは有効だが必須ではなく、違いが見える形にすればよい。利点/欠点の整理は、この対立軸の中でも特に使いやすい型として積極的に使う。

### 9. たとえ話と具体例で直感を掴ませる
コアアイデアや、数式・アルゴリズムなど読者がつまずきそうな箇所に絞って使う。テンプレートの `.example` ボックスは目立つので、記事の要になるたとえに使い、短いものは本文に溶かす。

## 推奨する記事構成テンプレート

論文や読者層によって調整してよいが、迷ったら次の骨格から始める。見出し記号は骨格を示すための便宜上の表記であり、実際の出力がHTMLの場合は `<h2>` 等に読み替える。

```markdown
# [タイトル: 何の技術か、何がすごいのかが一目で分かるように]

## 概要
(Introductionより前に置く一言サマリー。具体的に何をする技術で、どこに応用できるかを2〜3文で。
 ここだけ読んでも「何の記事か」が分かることが目標)

## この記事で学べること / こんな人におすすめ
- 箇条書きで2〜4個

## はじめに
- 読者が抱えていそうな疑問・課題を提示する("〜と思ったことはないだろうか")
- その論文が何を解決しようとしているかを短く述べる
- 可能なら、記事全体を貫く対立軸(既存手法 vs 提案手法、想定される反論とその回答など)を示す

## 事前知識 (必要な場合のみ)
- 読者が詰まりそうな前提知識を先出しする

## モチベーション・既存手法の課題
- なぜこの手法が必要とされたのか
- 既存手法の何が不十分だったのか
- 単発の課題提示で終わらせず、経緯が一つのストーリーとして繋がるように書く

## 提案手法のコアアイデア
- まず一言でコアコンセプトを述べる → その後に詳細を展開
- たとえ話・図解を入れる

## 手法の詳細
- 論文の構成に沿いつつ、情報の粒度を小さくしてセクション分割する
- 各セクションの冒頭で「このセクションで言いたいこと」を先に一言で示す
- 読者がつまずきそうな箇所(数式・アルゴリズム)には、たとえ話か具体例を添える
- 比較表・箇条書きを積極的に使う

## 利点と欠点 / 難しさ
- 表や箇条書きで整理する

## (あれば) 簡易実装で試してみる
- 最小限のコードで動作イメージを掴めるようにする
- 著者独自の切り口・実験があるとなお良い

## まとめ
- 要点の再掲
- 著者としての感想・今後の展望・関連研究へのポインタなど
```

## 書きながら意識するチェックリスト

- [ ] タイトルと最初の数行だけで「何の技術か」「なぜすごいのか」が伝わるか
- [ ] Introductionの前後で、読者の疑問・課題を言語化できているか
- [ ] 差分の説明で終わっておらず、全体像・経緯がストーリーとして繋がっているか
- [ ] 「この記事で学べること」が明記されているか
- [ ] 各セクションの冒頭で結論・要点を先出ししているか(詳細から入っていないか)
- [ ] 情報の粒度が大きすぎるセクションはないか(分割できないか)
- [ ] 図や表を入れられる箇所を見逃していないか
- [ ] 同じトーンの文章が長く(3〜4段落以上)続いている箇所を、図表・箇条書き・空行で区切れないか
- [ ] 箇条書き・比較表で整理できる文章を、長い段落のまま書いていないか
- [ ] 読者がつまずきそうな箇所に、たとえ話・具体例を添えられているか(逆に、重ねすぎてくどくなっていないか)
- [ ] 著者独自の視点(切り口・感想・簡易実装など)が入っているか
- [ ] 記事全体を貫く対立軸(二項対立)を設定できているか(仮想敵・ライバル手法・想定反論など)
- [ ] 良い点だけでなく、欠点・限界・難しさにも触れているか
- [ ] 論文の逐語訳・機械的な要約になっていないか(自分の言葉で咀嚼できているか)

## 出力形式

- デフォルトはHTMLで出力する。**`assets/article-template/article.html` をコピーし、`[PLACEHOLDER: ...]` を差し替えて書く。ゼロからHTML/CSSを設計しない。**
  - テンプレートはCSS/JSをインラインで持つ1ファイル完結型で、KaTeX(数式)・highlight.js(コード)・目次の自動生成・ダークモードまで組み込み済み。使い方と部品カタログ(たとえ話・具体例ボックス・対立軸ボックス・比較表・図版・コールアウト・利点/欠点・補足)はファイル内のコメントにある。
  - 見出しの並びは上の「推奨する記事構成テンプレート」と対応している。論文に合わせてセクションを削除・追加してよいが、デザイン(`<style>`・`<script>`)は変更しない。
- Markdownでの出力を求められた場合(Zenn/Qiita向けなど)はテンプレートを使わず、図はSVG/PNGファイルとして生成して `![alt](path)` で参照する。数式・コードの記法は投稿先の仕様に合わせる。
- 図は実際に作成して埋め込む。
  - 概念図・アーキテクチャ図・比較図・フロー図 → SVGを直接記述してインライン埋め込みする。
  - 数値データの比較・グラフ(削減率、精度比較など) → コード実行(matplotlibなど)で生成し、SVGのインライン埋め込みか base64 の data URI で埋め込む(別ファイル参照にしない)。ダークモードで文字が消えないよう、背景は透過にせず白のままにする。
  - 論文中の図を参考にする場合も、可能な範囲で読者を考えて自分で描き直し、出典(論文タイトル・著者・リンク)を明記する。
- 論文からの引用は要約・自分の言葉での説明を基本とし、原文の長い一節をそのまま転記しない。図表を論文から転載する場合は出典(論文タイトル・著者・リンク)を明記する。
